Ten dokument opisuje, jak firmware BEKO chroni komunikację radiową, sekrety lokalne, TPM, AES/\+HMAC, EEPROM, liczniki anti-\/replay i dostęp lokalny przez menu.

Dokument jest pisany z perspektywy aktualnego kodu firmware STM32 w katalogu {\ttfamily Core/\+App}. Jeżeli backend gatewaya albo frontend RPi zmieni protokół, ten plik należy zaktualizować razem z kodem.\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md81}{}\doxysection{\texorpdfstring{1. Skrót}{1. Skrót}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md81}
Najważniejsze decyzje bezpieczeństwa\+:


\begin{DoxyItemize}
\item TPM jest lokalnym root-\/of-\/trust dla noda.
\item Root seed urządzenia jest przechowywany w TPM NV index {\ttfamily 0x01\+C10101}.
\item Zapis root seeda do głównego indexu wymaga TPM Physical Presence ({\ttfamily PPWRITE}).
\item TPM PP jest podłączony bezpośrednio do TPM, pin {\ttfamily 7}, aktywny stanem {\ttfamily VDD}.
\item TPM komunikuje się z MCU przez {\ttfamily I2\+C3}, {\ttfamily PC0=SCL}, {\ttfamily PC1=SDA}.
\item {\ttfamily TPM\+\_\+\+RESET\#} jest na {\ttfamily PB0}, aktywny niskim stanem.
\item {\ttfamily TPM\+\_\+\+DAVINT\#} / {\ttfamily PIRQ} jest na {\ttfamily PH0}, aktywny niskim stanem.
\item Sekrety w EEPROM są szyfrowane kluczem wyprowadzonym z root seeda TPM.
\item Payload radiowy jest szyfrowany {\ttfamily AES-\/\+CTR}.
\item Integralność i autentyczność ramki zapewnia {\ttfamily HMAC-\/\+SHA256}.
\item HMAC obejmuje nagłówek i payload, czyli także {\ttfamily src\+\_\+id}, {\ttfamily dst\+\_\+id}, {\ttfamily msg\+\_\+id} i {\ttfamily counter}.
\item Odbiornik weryfikuje HMAC przed odszyfrowaniem payloadu.
\item Porównanie MAC jest stałoczasowe względem długości tagu.
\item Backend crypto używa sprzętowego AES/\+HASH STM32, jeżeli self-\/test przejdzie.
\item Jeżeli hardware crypto nie przejdzie self-\/testu, firmware używa software fallback.
\item Klucze i bufory tymczasowe są zerowane po użyciu przez {\ttfamily \doxylink{laviet__crypto_8c_ad8181b01dd76111b6f493f92d9a8f2b4}{laviet\+\_\+secure\+\_\+zero()}}.
\item Dostęp do menu chronią role lokalne i PIN operator/admin.
\item Logi TPM TIS można włączyć przez {\ttfamily TPM\+\_\+\+INIT\+\_\+\+LOG}; domyślnie verbose TPM init jest schowany.
\item Logowanie wrażliwych payloadów na UART jest kontrolowane przez {\ttfamily \doxylink{pager__config_8h_a6176f7b270798f1eb48d2d02c68dc4f3}{PAGER\+\_\+\+CONFIG\+\_\+\+UART\+\_\+\+SENSITIVE\+\_\+\+LOGS}}.
\end{DoxyItemize}

\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md82}{}\doxysection{\texorpdfstring{2. Cele bezpieczeństwa}{2. Cele bezpieczeństwa}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md82}
System chroni cztery główne obszary\+:


\begin{DoxyEnumerate}
\item Poufność wiadomości radiowych.
\item Integralność i autentyczność ramek.
\item Trwałe sekrety noda\+: root seed, trusted devices, pair code, countery.
\item Lokalny dostęp operatora/administratora.
\end{DoxyEnumerate}

System nie zakłada, że radio jest zaufane. Kanał radiowy jest traktowany jako publiczny\+:


\begin{DoxyItemize}
\item każdy może podsłuchać,
\item każdy może wysłać bajty,
\item każdy może powtórzyć starą transmisję,
\item każdy może próbować floodować,
\item pakiety mogą zginąć albo przyjść po czasie.
\end{DoxyItemize}

Dlatego bezpieczeństwo nie opiera się na Lo\+Ra/\+FSK/\+OOK jako takich. Radio jest tylko transportem. Ochrona jest w warstwie aplikacyjnej {\ttfamily LAVIET\+\_\+\+FRAME\+\_\+\+V1}.\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md83}{}\doxysection{\texorpdfstring{3. Model atakującego}{3. Model atakującego}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md83}
Zakładany atakujący może\+:


\begin{DoxyItemize}
\item słuchać kanału radiowego,
\item wysyłać własne pakiety SX1276/\+RFM95,
\item powtarzać stare ramki,
\item próbować zgadnąć {\ttfamily src\+\_\+id},
\item próbować podszyć się pod gateway albo node,
\item odczytać zewnętrzny EEPROM po fizycznym dostępie do płytki,
\item obserwować UART, jeżeli ma dostęp serwisowy,
\item zresetować zasilanie w niekorzystnym momencie.
\end{DoxyItemize}

Zakładany atakujący nie powinien móc\+:


\begin{DoxyItemize}
\item odczytać sekretów z TPM bez obejścia zabezpieczeń TPM,
\item zapisać nowego root seeda bez fizycznej obecności TPM PP,
\item wygenerować poprawnego HMAC bez właściwego klucza,
\item zmodyfikować zaszyfrowanej wiadomości tak, żeby przeszła HMAC,
\item udawać sparowanego peer-\/a po zakończonym pairingu bez pair code.
\end{DoxyItemize}

Ważne\+: jeżeli atakujący ma pełny dostęp debug/\+SWD do działającego MCU i może czytać RAM, może próbować odczytywać klucze w czasie użycia. Ten projekt ogranicza czas życia sekretów w RAM, ale nie zastępuje pełnej ochrony debug portu, secure boot ani Trust\+Zone policy.\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md84}{}\doxysection{\texorpdfstring{4. \hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md86}{}\doxysection{\texorpdfstring{6. TPM jako root-\/of-\/trust}{6. TPM jako root-\/of-\/trust}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md86}
TPM jest używany po to, żeby główny sekret urządzenia nie był stałą w firmware ani zwykłym bajtem w EEPROM.

Obecny TPM\+:


\begin{DoxyItemize}
\item model/rodzina\+: ST33\+KTPM2X,
\item adres I2C 7-\/bit\+: {\ttfamily 0x2E},
\item magistrala\+: {\ttfamily I2\+C3},
\item linie\+: {\ttfamily PC0=SCL}, {\ttfamily PC1=SDA},
\item reset\+: {\ttfamily TPM\+\_\+\+RESET\#} na {\ttfamily PB0}, aktywny {\ttfamily GND},
\item interrupt/data available\+: {\ttfamily TPM\+\_\+\+DAVINT\#} na {\ttfamily PH0}, aktywny {\ttfamily GND},
\item physical presence\+: TPM pin {\ttfamily 7}, aktywny {\ttfamily VDD}, podłączony do TPM, nie do GPIO MCU.
\end{DoxyItemize}\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md87}{}\doxysubsection{\texorpdfstring{6.\+1. Dlaczego TPM jest bezpieczniejszy niż EEPROM}{6.\+1. Dlaczego TPM jest bezpieczniejszy niż EEPROM}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md87}
EEPROM jest tylko pamięcią. Jeśli ktoś fizycznie odczyta EEPROM, dostaje zapisane bajty.

TPM jest układem bezpieczeństwa\+:


\begin{DoxyItemize}
\item ma własne komendy i polityki autoryzacji,
\item może wymagać platform auth albo physical presence,
\item nie udostępnia NV write bez spełnienia atrybutów indexu,
\item wykonuje {\ttfamily TPM2\+\_\+\+Get\+Random},
\item separuje trwały sekret od zwykłej pamięci aplikacji,
\item pozwala przechowywać root seed poza firmware.
\end{DoxyItemize}

W tym projekcie TPM nie jest używany jako “magiczne szyfrowanie wszystkiego”. TPM jest korzeniem hierarchii kluczy. To oznacza, że z niego pochodzi materiał, który potem zasila klucze robocze.\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md88}{}\doxysection{\texorpdfstring{7. TPM init}{7. TPM init}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md88}
Podczas startu {\ttfamily security\+\_\+main} wykonuje\+:


\begin{DoxyEnumerate}
\item Konfigurację drivera TPM przez {\ttfamily \doxylink{st33ktpm2x_8c_a4395b053468eaa84de32315c833c9a2e}{st33ktpm2x\+\_\+default\+\_\+cfg}(\&cfg, \&hi2c3)}.
\item Hard reset TPM przez {\ttfamily TPM\+\_\+\+RESET\#}.
\item Opcjonalny odczyt {\ttfamily DAVINT\#}.
\item Skan/probe I2\+C3, jeśli {\ttfamily TPM\+\_\+\+INIT\+\_\+\+LOG} jest aktywny.
\item Odczyt identyfikacji TPM ({\ttfamily DID\+\_\+\+VID}, {\ttfamily RID}).
\item {\ttfamily TPM2\+\_\+\+Startup(\+ST\+\_\+\+CLEAR)}.
\item {\ttfamily TPM2\+\_\+\+Self\+Test(full\+\_\+test=false)}.
\item Ustawienie {\ttfamily s\+\_\+tpm\+\_\+ready=true}, jeśli transport i podstawowe komendy działają.
\end{DoxyEnumerate}

Sam root seed jest ładowany z TPM podczas startu.\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md92}{}\doxysubsection{\texorpdfstring{8.\+2. Lifecycle root seeda}{8.\+2. Lifecycle root seeda}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md92}
Przy starcie firmware wykonuje\+:


\begin{DoxyEnumerate}
\item Próbuje odczytać {\ttfamily 0x01\+C10101}.
\item Jeśli główny index nie ma danych, próbuje legacy index {\ttfamily 0x01\+C10100}.
\item Jeśli legacy seed istnieje, firmware próbuje migrować go do PP-\/protected index.
\item Jeśli nie ma żadnego seeda, firmware generuje nowy seed.
\item Jeśli TPM jest gotowy, nowy seed jest zapisywany do TPM NV.
\item Zapis do {\ttfamily 0x01\+C10101} wymaga aktywnego TPM PP.
\item Seed jest używany do wyprowadzenia kluczy.
\item Bufory tymczasowe z seedem są zerowane.
\end{DoxyEnumerate}

\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md93}{}\doxysubsection{\texorpdfstring{8.\+3. Physical Presence}{8.\+3. Physical Presence}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md93}
Physical Presence ({\ttfamily PP}) jest ważne, bo chroni operacje, które zmieniają root seeda.

W obecnym hardware\+:


\begin{DoxyItemize}
\item przycisk PP jest podłączony do TPM pin {\ttfamily 7},
\item aktywny poziom to {\ttfamily VDD},
\item STM32 nie odczytuje PP jako GPIO,
\item TPM sam egzekwuje warunek dla operacji {\ttfamily PPWRITE}.
\end{DoxyItemize}

To oznacza\+:


\begin{DoxyItemize}
\item firmware nie może “udawać” fizycznej obecności przez samo ustawienie GPIO,
\item zdalny atak radiowy nie powinien móc nadpisać root seeda,
\item operator musi fizycznie nacisnąć/aktywować PP podczas rotacji wymagającej zapisu.
\end{DoxyItemize}\hypertarget{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md94}{}\doxysubsection{\texorpdfstring{8.\+4. Ograniczenie\+: seed ma 8 bajtów}{8.\+4. Ograniczenie\+: seed ma 8 bajtów}}\label{md_Core_2App_2security_2SECURITY__ARCHITECTURE_autotoc_md94}
Aktualny root seed ma {\ttfamily 8 B}, czyli 64 bity.

To jest istotne ograniczenie. Architektura hierarchii kluczy jest poprawna, ale dla długoterminowego bezpieczeństwa produkcyjnego lepiej zwiększyć seed do {\ttfamily 16 B} albo {\ttfamily 32 B}.

Dlaczego mimo tego obecny model jest lepszy niż stały klucz\+:


\begin{DoxyItemize}
\item seed nie jest stałą firmware,
\item seed może być inny per urządzenie,
\item seed jest w TPM,
\item zapis wymaga PP,
\item klucze robocze są separowane labelami HMAC.
\end{DoxyItemize}

Software fallback istnieje jako zabezpieczenie dostępności.

Jeżeli hardware AES/\+HASH\+:


\begin{DoxyItemize}
\item nie jest gotowy,
\item nie przejdzie self-\/testu,
\item zwróci błąd HAL,
\item nie da się zablokować mutexa,
\end{DoxyItemize}

Dlaczego to jest bezpieczne\+:


\begin{DoxyItemize}
\item system nie przechodzi na “brak crypto”,
\item nadal liczy HMAC,
\item nadal szyfruje AES-\/\+CTR,

\end{DoxyItemize}

\begin{DoxyItemize}
\item software AES/\+HMAC działa w RAM MCU i może być wolniejszy,
\item przy pełnym modelu produkcyjnym trzeba też chronić debug/\+SWD i pamięć.

Bo sekret główny nie jest w firmware ani w EEPROM, tylko w TPM; zapis sekretu wymaga fizycznej obecności; klucze robocze są wyprowadzane z separacją domen; każda ramka jest uwierzytelniana HMAC po nagłówku i payloadzie; payload jest szyfrowany AES-\/\+CTR z nonce/counter zależnym od ramki; błędny hardware crypto jest wykrywany self-\/testem; EEPROM trzyma sekrety zaszyfrowane kluczem wyprowadzonym z TPM; a lokalne operacje konfiguracyjne są chronione PIN-\/em i menu role.
